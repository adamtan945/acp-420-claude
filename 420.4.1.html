Request types

Request type 是 customer 在 portal 看到的「我要什麼」。這節最大、細節最多：對應的 issue type、portal 分組、表單欄位、customer 看到的 status 名稱與限制誰能提。

3 分鐘速覽

Request type＝customer 看到的入口；issue type＝背後的引擎

  1. 一個 request type 只對一個 issue type一個 issue type 可以給很多 request type 用；workflow 與欄位來自 issue type。
  2. Portal groups 決定 portal 怎麼分類一個 request type 可在多個 group；從所有 group 移除＝從 portal 藏起來（搜尋仍找得到）。
  3. Request form vs issue viewRequest form 給 customer 填；issue view 給 agent 看；兩邊欄位分開設定。
  4. Use preset value and hide from portal自動填值並對 customer 隱藏；portal 不支援的欄位（Assignee、Linked issues）只能這樣用。
  5. Status name to show customer替 customer 改 status 的顯示名稱；同名可藏掉 transition。
  6. Restrictions限定哪些 user、group、customer、organization 能提這種單（最多 50 個）；只管「提」，不管「看」。

  • 改 work item 的 issue type 就要跟著改 request type。
建立與分組

建立、刪除、portal groups

  1. 建立Space settings → Request management → Request types → Create request type：Create blank（名稱、說明、icon、portal group、issue type），或 Create from template（只有 Jira admin）。
  2. Work category把 request type 放進 Service requests、Incidents、Changes… 分類，決定它出現在哪個側欄區塊。
  3. Portal groupsSpace settings → Channels & self service → Portal → Portal Groups：Create group、Add request form、拖拉排序。超過一個 group 才會在 portal 顯示分組。
  4. 藏起來把 request type 從所有 portal group 移除＝customer 在 portal 首頁看不到（搜尋仍可找到、可放進 help center topic）。
  5. 刪除有 request 在用時會警告，要把它們改到新的 request type。Email 用的 request type 要先關 email requests 才能刪。

Field configuration 的必填 vs request type 的必填

Field configuration（Jira admin）設必填 → 這個 issue type 在任何地方建立都要填；request form 上沒放又沒 preset，customer 會建不起來。Request type 的 Required 只影響這張 portal 表單。要「只在 portal 必填」就在 request type 設，要「全站一律必填」才動 field configuration。

Status 與限制

Customer 看到的 status、誰能提單

  • Status name to show customer：Request types → 選 request type → Workflow Statuses：把 In Progress 顯示成「處理中」、Waiting for support 顯示成「已收到」。
  • 把兩個 status 設成同一個顯示名稱，customer 就看不到這兩個 status 之間的 transition。
  • Restrictions：Request type → Restrictions → 加入可以提單的 user、group、customer account、organization（最多 50 個）；沒權限的人在 portal 連看都看不到（搜尋也不行），admin 與 agent 也一樣，除非加進名單。
  • 限制不適用 email、chat、widget、virtual agent：這些管道用到的 request type 一旦被限制，對任何人都不會出現。
  • Automation、change management 與 app user 預設沒有存取被限制的 request type；要另外把 app user 或 atlassian-addons-admin 加進名單。
  • Restrictions 只管「誰能提」，不管「誰能看」——要限制誰看得到 request，用 issue security level。
本段必考
  • 同名 status＝藏 transition。
  • Restrictions 管提單，issue security 管看。
