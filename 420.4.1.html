Request types

Request type 是 customer 在 portal 看到的「我要什麼」。這節最大、細節最多：對應的 issue type、portal 分組、表單欄位、customer 看到的 status 名稱與限制誰能提。

3 分鐘速覽

Request type＝customer 看到的入口；issue type＝背後的引擎

  1. 一個 request type 只對一個 issue type一個 issue type 可以給很多 request type 用；workflow 與欄位來自 issue type。
  2. Portal groups 決定 portal 怎麼分類一個 request type 可在多個 group；從所有 group 移除＝從 portal 藏起來（搜尋仍找得到）。
  3. Request form vs issue viewRequest form 給 customer 填；issue view 給 agent 看；兩邊欄位分開設定。
  4. Use preset value and hide from portal自動填值並對 customer 隱藏；portal 不支援的欄位（Assignee、Linked issues）只能這樣用。
  5. Status name to show customer替 customer 改 status 的顯示名稱；同名可藏掉 transition。
  6. Restrictions限定哪些 user、group、customer、organization 能提這種單（最多 50 個）；只管「提」，不管「看」。

建立與分組

建立、刪除、portal groups

  1. 建立Space settings → Request management → Request types → Create request type：Create blank（名稱、說明、icon、portal group、issue type），或 Create from template（只有 Jira admin）。
  2. Work category把 request type 放進 Service requests、Incidents、Changes… 分類，決定它出現在哪個側欄區塊。
  3. Portal groupsSpace settings → Channels & self service → Portal → Portal Groups：Create group、Add request form、拖拉排序。超過一個 group 才會在 portal 顯示分組。
  4. 藏起來把 request type 從所有 portal group 移除＝customer 在 portal 首頁看不到（搜尋仍可找到、可放進 help center topic）。
  5. 刪除有 request 在用時會警告，要把它們改到新的 request type。Email 用的 request type 要先關 email requests 才能刪。

Field configuration 的必填 vs request type 的必填

Field configuration（Jira admin）設必填 → Jira 建立 work item 時都會要求有值；欄位必填卻不在 request form 上、也沒有 preset，customer 會送不出（官方 KB：customers unable to submit tickets due to required fields）。Request type 的 Required 只影響這張 portal 表單。要「只在 portal 必填」就在 request type 設。

Status 與限制

Customer 看到的 status、誰能提單

  • Status name to show customer：Request types → 選 request type → Workflow Statuses：把 In Progress 顯示成「處理中」、Waiting for support 顯示成「已收到」。
  • 把兩個 status 設成同一個顯示名稱，customer 就看不到這兩個 status 之間的 transition。
  • Restrictions：Request type → Restrictions → 加入可以提單的 user、group、customer account、organization（最多 50 個）；沒權限的人在 portal 連看都看不到（搜尋也不行），admin 與 agent 也一樣，除非加進名單。
  • 限制不適用 email、chat、widget、virtual agent：這些管道用到的 request type 一旦被限制，對任何人都不會出現。
  • Automation、change management 與 app user 預設沒有存取被限制的 request type；要另外把 app user 或 atlassian-addons-admin 加進名單。
  • Restrictions 只管「誰能提」，不管「誰能看」——要限制誰看得到 request，用 issue security level。
本段必考
  • 同名 status＝藏 transition。
  • Restrictions 管提單，issue security 管看。

動手做

實作 Lab：建一個 request type，藏起來、再限制

約 30 分鐘HELP 的 project admin（Create from template 只有 Jira admin）

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：從零建一個 request type，調整 request form 的欄位與 customer 看到的 status 名稱，再用 portal group 與 restrictions 控制誰看得到、誰能提。

這個 Lab 對應的考點

一個 request type 只對一個 issue type；從所有 portal group 移除＝藏起來（搜尋仍找得到）；Preset＋hide＝自動填、customer 看不到；同名 status＝藏 transition；Restrictions 只管「提」不管「看」。

準備

  • Cara（Acme Corp）與 Dan 都能登入 HELP 的 portal，各用一個瀏覽器設定檔。
  • 這個 Lab 建的 Lab 借用投影機 會在 420.4.2～420.4.4 繼續用，收尾時不要刪。

步驟

  1. 你應該看到：清單多了 Lab 借用投影機，旁邊標著你選的 work type。它的 workflow 和欄位來源就是這個 work type。
  2. 你應該看到：Summary 只能改名，沒有移除或隱藏的選項；Assignee 那一列顯示 preset 值 Leo。
  3. 你應該看到：表單第一格叫「借用事由」，Due date 有必填標記；看不到 Assignee。送出一張 request。
  4. 你應該看到：Assignee 已經是 Leo（preset 值自動填入）；Leo 在 work item 上看得到這個欄位。
  5. 你應該看到：Cara 的 portal 從頭到尾都顯示「處理中」，看不出中間轉過一次：同名 status 會把 transition 藏起來。
  6. 你應該看到：首頁的分類裡看不到它；搜尋仍找得到。這是「藏起來」，不是刪除。
  7. 你應該看到：Cara 看得到也能提單；Dan 在首頁與搜尋都找不到它。你自己（admin）不在名單上，從 portal 也提不了這種單。

試試看：改一個設定，觀察差異

T1在 Request form 的右側面板搜尋 Reporter、Security level、Request participants。看結果
通常找不到：這幾個屬於不能加進 request type 的欄位。Assignee、Linked issues 這類則能加，但只能 preset 並隱藏。
T2步驟 7 的 restriction 還在時，用 Leo 打開 Cara 先前提的那張 request。看結果
Leo 仍看得到、能處理。Restrictions 只管誰能「提」，不管誰能「看」；要限制檢視得用 issue security level。
T3（想像，不實際做）Jira admin 在 field configuration 把某個 custom field 設成必填，但 Lab 借用投影機的 request form 上沒有這個欄位、也沒有 preset。看結果
Customer 會送不出 request。Field configuration 的必填是全面的；只想在這張表單必填，就在 request type 勾 Required。
心像錨點：閉上眼睛想一次這個畫面

Request types 清單裡 Lab 借用投影機那一列：右邊寫著它的 work type。前台 request type、後台 work type；藏＝移出所有 group，限＝只管提。

收尾

  • 移除 Lab 借用投影機的 restriction（Restrictions → Remove → Apply），確認它回到 portal group。
  • Workflow Statuses 改回原本的顯示名稱。保留 Due date 必填與 Assignee preset，420.4.3 會用到。
