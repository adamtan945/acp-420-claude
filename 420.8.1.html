什麼時候用 automation

考你看懂業務需求，判斷要不要用 automation、用哪一種 trigger，以及何時以 automation 取代內建通知。

3 分鐘速覽

什麼時候該用 automation

  1. 重複性工作自動更新欄位、指派、轉 status、寄通知——人每天手動做同一件事，就是 automation 的候選。
  2. SLA 快違約SLA threshold breached trigger：違約前 X 分鐘通知 agent、提高 priority、留言給 customer。
  3. 取代內建通知內建 customer／internal notification 不夠細時，用 automation 寄更貼切的訊息（特定 request type、特定時機、特定收件人）。
  4. 連動 AssetsWork item 到某 status 時，Edit object／Assets 動作把設備的 Status 屬性改成 In repair。
  5. 不是什麼都要 automation一次性的大量修改用 bulk change；每次 transition 必做且要保證一致的用 post function。
  6. Auto-resolve／auto-closeWaiting for customer 超過 N 天沒回 → 自動解決並通知。
判斷

需求 → 該不該用 automation

Customer 3 天沒回就自動關單
Scheduled trigger＋JQL＋Transition（auto-close）
SLA 剩 30 分鐘時通知 team lead
SLA threshold breached（before breach）＋Send email／Slack
只有「Laptop request」在 Ready for pickup 時寄取件說明給 customer
Automation（取代內建通知）
Request 到 Repair 時把筆電 Status 設為 In repair
Automation：Edit object／Assets 動作
一次把 300 張舊 request 的 priority 改掉
Bulk change（不是 automation）
每次轉 Resolved 都要設 resolution
Workflow post function
本段必考
  • 週期性、事件驅動、要判斷條件 → automation。
  • 一次性 → bulk；每次 transition 必做 → post function。
通知

Automation vs 內建通知

需求內建 customer／internal notificationAutomation
每個事件固定通知參與者✓ 最簡單可，但不必要
只針對某個 request type 或某個 status✗ 規則是 project 全域的✓ 用 condition 限定
寄給非參與者（主管、外部 email、Slack 頻道）✗✓ Send email／Slack／Teams
提醒（N 天沒回、到期前）✗✓ Scheduled 或 SLA trigger
內容依欄位值變化部分（variables）✓ smart values＋if/else
避免重複通知

用 automation 取代某個內建通知時，記得把對應的 customer notification 規則關掉（Enable off），否則 customer 會收到兩封。

本段必考
  • 要更「對的人、對的時機、對的內容」→ automation。
