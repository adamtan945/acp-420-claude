3 分鐘速覽

Rule 出錯時從哪裡查

  1. Scope單一 project（project admin 可建）vs 多個 project／project type／global（要 Jira admin）；多 project rule 改一次影響全部。
  2. Audit log每次執行的狀態與每一步細節；保留 90 天。
  3. Log action把 smart value 的值寫進 audit log，用來除錯。
  4. Status pageAutomation service status page：確認是不是 Atlassian 服務本身出問題。
  5. Owner錯誤時收 email；人離職或休假要 transfer（Jira admin 用 Transfer user）。
  6. Performance insights執行次數、平均與總時間；Success、No action、Some errors、Loop、Throttled。

Scope

單一 project vs 多個 project

Single projectMultiple projects／project type／Global
誰能建Project adminJira admin（global automation）
影響只在這個 project改一次影響所有在 scope 的 project
Usage（現行）以 automation step 計：trigger、condition、action、branch、loop 每執行一次算一步同左；額度在 organization 層級共用，不再按 app 或 project 分開計
注意—欄位、status、request type 名稱在各 project 必須一致；權限要涵蓋所有 project

  • 多 project rule 要 Jira admin。
  • Scope 越大，改錯影響越大。

除錯

Audit log 與 log action

  1. 看 audit logRule → Audit log：時間、狀態（Success、No actions performed、Some errors、Throttled、Loop）、每個步驟的細節。保留 90 天。
  2. 加 Log action在可疑步驟前加 Log action，例如記錄 {{issue.Affected services.tier}}，看 smart value 是不是你以為的值。
  3. 看 status page大量 rule 同時失敗或延遲時，先查 Atlassian automation 的服務狀態頁。
  4. 常見原因Condition 不符（No actions performed）、actor 沒權限、欄位不在 screen、request type 對不上 issue type、達到 service limit（Throttled）、rule 互相觸發（Loop）。
Audit log 狀態意思
Success做了 action
No actions performed觸發了，但 condition 擋下
Some errors有步驟失敗
Throttled超過 service limit
LoopRule 互相觸發形成迴圈
本段必考
  • No actions performed＝condition 不符，不是錯誤。
  • Log action 是除錯神器。

Performance insights

看效能與 service limit 風險

  • Rule 清單 → More actions → View performance insights：execution count、average duration、total duration。
  • 依結果分：Successful、No action、Some errors、Loop、Throttled。
  • Throttled 多 → 接近 service limit：縮小 scope、改用更精準的 trigger 與 JQL、減少 branch 與 web request。
  • Audit log 的 Total time 包含處理時間：Delay、Send web request 等待、多個 branch 都算進去。
本段必考
  • Throttled＝撞到 service limit。

動手做

實作 Lab：讀 audit log，把 rule 交給別人

約 25 分鐘HELP 的 project admin；Transfer user 與 multi-space／global scope 要 Jira admin

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：故意讓 rule 一次被 condition 擋下、一次出錯，從 audit log 判讀；再看 owner、actor、scope、Transfer user 與 performance insights。

這個 Lab 對應的考點

Audit log 保留 90 天；No actions performed＝condition 不符，不是錯誤；owner 收錯誤通知、actor 執行變更；多 project 或 global scope 要 Jira admin；Transfer user 一次換掉 owner、actor 與 user picker 裡的人（connection owner 例外）；Throttled＝撞到 service limit。

準備

  • 沿用 420.8.1 的「Lab 取件說明」（或任一條 project rule）。

步驟

  1. 你應該看到：看得到觸發時間、Status、Total time，以及每個步驟的細節與執行時間。
  2. 你應該看到：新的一筆是 No actions performed：condition 不符，rule 照設計停下，不是壞掉。
  3. 你應該看到：這次是錯誤狀態（例如 Some errors），步驟細節寫出 request type 對不上 work type。修好之前先刪掉這個 action。
  4. 你應該看到：Audit log 印出 rule 執行當下讀到的值；值不如預期，就知道 condition 為什麼不符。
  5. 你應該看到：Owner 預設是你（出錯時收 email）；actor 預設是 Automation for Jira。Scope 停在這個 space；改成多個 space 或 global 要 Jira admin。
  6. 你應該看到：預覽列出會被更新的 rule 與次數：owner、actor、user picker 裡的人都會被換掉；connection owner 不在其中。
  7. 你應該看到：Execution count、average duration、total duration，依 Successful、No action、Some errors、Loop、Throttled 分開統計。

試試看：改一個設定，觀察差異

T1（想像，不實際做）同時有大量 rule 失敗或延遲，而你的設定都沒改過。看結果
先查 Atlassian 的 automation service status page，確認是不是服務本身出問題，再查 audit log。
T2（想像，不實際做）rule A 的留言觸發 rule B，rule B 又改欄位觸發 rule A，而兩條都勾了 Allow rule trigger。看結果
Audit log 與 performance insights 會出現 Loop。檢查 Allow rule trigger 與 trigger 條件，打斷互相觸發。
T3把「Lab 取件說明」的 Owner 改成 Ana，再故意弄出一次錯誤。看結果
錯誤 email 寄給 Ana 不寄給你：owner 收錯誤通知，actor 才是執行者。做完改回。
心像錨點：閉上眼睛想一次這個畫面

Audit log 表格：三行狀態並排，Success、No actions performed、Some errors。範圍、日誌、狀態頁、主人、效能；owner 收信、actor 動手。

收尾

  • 刪除為了弄錯而加的 Edit request type action 與 Log action。
  • 確認 owner 改回你自己；Transfer User 沒有送出。
  • 不再需要的 Lab rule 停用或刪除。
