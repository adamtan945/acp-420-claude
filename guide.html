420.1・16%

420.1 使用者、角色與權限

420.1.1 使用者、角色與權限類型

付費三人組Admin、agent、collaborator（collaborator 付的是 Jira）。
免費三人組Customer、participant、organization。
Customer 權限走 Portal Access不是走 role。
  1. Agent＝佔 JSM 授權在 Service Desk Team role；看 queue、回覆 customer、管 customer 與 organization。
  2. Collaborator＝有 Jira 授權但不是 agent也放在 Service Desk Team role；只能看、加 internal comment、加附件、記工時、watch。
  3. Customer＝免費從 portal、email、widget 提單；只看得到自己的（或被分享的）request。
  4. Request participant＝被分享 request 的人跟 reporter 收一樣的通知；仍受 issue security 限制。
  5. Organization＝customer 的群組可跨 service project 重複用；跟 Atlassian organization（admin 用的）是兩回事。
  6. 五種權限Product access → Global → Permission scheme → Customer permissions → KB permissions。
本節所有「本段必考」（7 條）
  • Agent 佔 JSM 授權；collaborator 佔 Jira 授權、只能 internal comment。
  • Customer、participant、organization 都免費。
  • Organization（customer 群組）≠ Atlassian organization。
  • Customer 權限給 Portal Access security type，不給 role。
  • Agent 與 collaborator 都在 Service Desk Team role。
  • Product access 決定授權；permission scheme 決定 project 內的動作。
  • Customer permissions 分兩層：site（customer access）＋project（channel access、sharing）。

420.1.2 Customers 與 organizations

Site 管能不能建帳號，project 管能不能進門Customer access vs channel access。
Open 跟著 site 走Restricted 只看邀請名單。
Detail 全站、五十、只改名
  1. Customer access（site admin）Settings → Products → JSM → Customer access：允不允許 customer 自己建帳號、要不要登入。
  2. 匿名提單Allow customers to create accounts＋勾 Customers can access and send requests from the portal without logging in；project 的 Channel access 選 Open。
  3. Channel access（project admin）Open＝沿用 site 的設定；Restricted＝只有被 agent／admin 邀請進這個 project 的 customer。
  4. Chat 不受 channel access 限制Restricted 時，Slack、Teams 提單的人會被自動邀請進 project。
  5. Customer sharing決定 customer 在 portal 用 Share with 能找誰：同 organization、或同 project、或輸入 email。
  6. Detail fieldsCustomer 與 organization 的 detail fields 是全站共用（不是只在這個 project），最多 50 個；建好後只能改 label。
本節所有「本段必考」（7 條）
  • Open＝沿用 site；Restricted＝只有被邀請進 project 的人。
  • 匿名提單要 site 與 project 兩邊都開。
  • 讓 customer 選 approver → sharing 選「space 或 organization 內搜尋」。
  • 要分享給整個 organization → 開 Sharing requests with organization。
  • Organization 跨 project 共用。
  • Email domain 只影響之後新加入的 customer。
  • Detail fields 全站共用、最多 50 個、只能改 label。

420.1.3 管理團隊成員

Team role 收兩種人有 JSM 授權＝agent；只有 Jira 授權＝collaborator。
預設指派只有兩個選項Unassigned 或 project lead。
看不到先查 ReporterSecurity level 有沒有包含提單人。
  1. 加 agentInvite team：輸入 email → 加進 Service Desk Team role。Project admin 只能加「已經有 JSM 授權」的人；全新的 agent 要 org admin。
  2. 加 collaborator把有 Jira 授權（無 JSM 授權）的人加進 Service Desk Team role。
  3. Role 成員 vs group 成員Project admin 能管 role 成員；group 成員只有 Administer Jira 才能改。
  4. Project lead 與 default assigneeProject admin 可改；default assignee 只能是 Unassigned 或 project lead。
  5. 指派的五種方式手動、project default assignee、component lead、request form 上預設（隱藏）的 Assignee、automation。
  6. Issue security 用 roleSecurity level 加 Service Desk Team role（或 reporter）就能只讓 agent 與提單人看到。
本節所有「本段必考」（7 條）
  • Agent 與 collaborator 都進 Service Desk Team role，差在有沒有 JSM 授權。
  • 新 agent 要 org admin。
  • Default assignee 只能 Unassigned 或 project lead。
  • 表單預設 Assignee＝隱藏欄位＋Portal Access 要有 Assign 權限。
  • Security level 用 role＋Reporter 最常見。
  • Participant 也受 security level 限制。
  • 排查順序：產品存取 → role → permission scheme → customer permissions → issue security。

420.2 Agent 端功能

420.2.1 Queues

Queue＝filter篩、排、欄位三件事。
沒分組就不刷新View all queues 收合不更新。
Remaining 含違約要排除加 != breached()。
  1. Queue 是一種 filter依 request type、status、JQL 篩出 request；可設欄位與排序。
  2. Project admin 建立與編輯Queues 旁 More actions → Queue settings → Create new queue。
  3. Priority groups把 queue 分組給不同團隊；一個 queue 可屬於多個 group；沒進 group 的在「View all queues」（考綱稱 Other）。
  4. 會自動更新數字的只有 Starred 與 priority groupsView all queues 不刷新、預設收合；數字到 999 顯示 999+。
  5. SLA 函數排 queue"Time to first response" < remaining("2h")、breached()、paused()…
  6. 上限每個 service project、每個 work category 最多 300 個 queue。
本節所有「本段必考」（8 條）
  • Queue＝JQL filter＋欄位＋排序。
  • Project admin 建立、編輯、排序。
  • 一個 queue 可屬於多個 group。
  • 沒分組的在 View all queues（Other），不刷新。
  • breached＝最後一次違約；everBreached＝曾經違約。
  • customerDetail／organizationDetail 只用 IN、NOT IN。
  • 多個簡單 queue 優於一個複雜 queue。
  • 個人 queue 用 currentUser()。

420.2.2 SLAs

開、停、暫、目標、日曆SLA 五個零件。
由上而下第一個Goal 的比對規則。
名字定了不能改
  1. ConditionsStart（開始計時）、Pause（暫停，選填）、Stop（停止）；多個條件任一符合就生效。
  2. Goals每個 goal＝JQL（哪些 work item）＋time target＋calendar；由上而下比對，第一個符合的生效。
  3. Calendar時區、工作日、時段（可多段，例如扣掉午休）、假日；預設 09:00–17:00。
  4. Priority 分組Goal 下可加 priority，每個 priority 各自的 target；All remaining priorities 兜底；最多 90 個 goal。
  5. 名稱建好就不能改所以要取清楚的名字，例如 Time to first response。
  6. 新 SLA 套到所有 work item包含已關閉的；編輯後進行中的 cycle 會重算或被丟棄。
本節所有「本段必考」（9 條）
  • Start、Pause、Stop；pause 選填。
  • Goal＝JQL＋target＋calendar。
  • 由上而下，第一個符合的 goal 生效。
  • 沒有 goal 符合＝沒有 SLA。
  • 最多 90 個 goal。
  • Calendar 決定「什麼時候」算時間；pause 決定「什麼狀態」不算。
  • 新 SLA 套用到所有 work item（含已關閉）。
  • 改 SLA 不會改寫已完成的 cycle。
  • Goal 順序：具體的放上面，兜底的放最後。

420.2.3 Features 開關

五個 category：請、斷、根、變、檢Service request、Incident、Problem、Change、PIR。
後三個要 PremiumProblem、Change、PIR。
  1. 位置Space settings → Features：用開關啟用或停用功能。
  2. Board 與 calendar考綱寫在 Feature tab；現行 Cloud 改在 queue 上用 Add to navigation 加 board、calendar view（Jira admin 或 space admin）。
  3. Work categoriesService requests、Incidents、Problems、Changes、Post-incident reviews；決定側欄分區與 request type 分類。
  4. 方案限制Problem、Change、major incident、post-incident review 只有 Premium／Enterprise（2024/10/16 起）。
  5. Alerts、On-call 任何 project 都能開；Services 只有 ITSM project在非 ITSM project 開這些要 Jira admin。
  6. Feature labFeatures 頁最下方，試用尚未正式發布的功能。
本節所有「本段必考」（4 條）
  • 一般請求→Service requests；中斷→Incidents；根因→Problems；變更→Changes；事後→PIR。
  • Services 只有 ITSM project；Alerts、On-call 都可以。
  • Alert P1–P5；可以跟 incident priority 不同。
  • Priority 變高，通知流程重來。

420.2.4 On-call

改、分、催、排Alert policy 改、routing 分、escalation 催、schedule 排。
Schedule 不催Route 到 schedule 不會 escalate。
  1. Schedule一組 rotation；可有多個 schedule（依時區、服務、地點）。三層：Base、Overrides、Final。
  2. Rotation輪流值班的一群人：shift duration＋frequency（daily、weekly、custom）＋participants。
  3. Routing rulesAlert 進到 team 時由上而下比對，第一個符合的決定交給 escalation、schedule 或 No one；最多 100 條。
  4. Escalation policy依順序通知；沒人 acknowledge 就通知下一步；acknowledge 或 close 就停。
  5. Alert policyAlert 建立時先改屬性（priority、訊息、responders）；global 先、team 後，由上而下。
  6. Free／Standard 限制只能 1 條自訂 routing rule；escalation 沒有 next／previous／random、repeat。
本節所有「本段必考」（7 條）
  • 順序：alert policy → routing rule → escalation → schedule。
  • Override 不改 base，只蓋一層。
  • No one 也是合法的 participant。
  • Routing：第一個符合；escalation：一步一步。
  • 交給 schedule 不會 escalate。
  • Alert policy 改 alert；routing rule 決定交給誰。
  • Global 先於 team。

420.3 為工單加上脈絡

420.3.1 Assets

庫、類、件、性Schema、type、object、attribute。
雙向連結Request 看 object、object 看 request。
  1. 考綱明說只考使用Utilize, but not configure：認得 schema、object type、object、attribute，會在 request 裡引用它們。
  2. 四層Object schema → object type → object → attributes。
  3. Object schema一組相關資料（例如 IT 資產）；有自己的權限。
  4. Object type同類 object 的群組（Laptop、Server）；可有 parent／child、繼承 attributes、可設 abstract。
  5. Assets object 欄位Jira 的 custom field，讓 request 連到 object；雙向連結，object 頁看得到相關 work item。
  6. 在哪用Request type 表單、forms、queue 欄位、JQL、automation（AQL）。
本節所有「本段必考」（4 條）
  • Schema → type → object → attribute。
  • Reference attribute 把 object 串起來。
  • Assets object 欄位＝雙向連結。
  • Filter scope 依 Assets；filter work scope 依目前 work item（可用 placeholder）。

420.3.2 Services

級、主、核、應、關Tier、owner、change approvers、responders、references。
加了不會自己動通知要 responder、priority 要 automation。
  1. Service 是全站的跨所有 service project 使用；考試版在 Features 開 Services（只有 ITSM project）。
  2. 每個 service 有Tier、owner team、change approvers、responders、stakeholders、references（依賴其他 service）、type（只是分類）。
  3. Tier 1–4Tier 1 最關鍵；可當 automation 與 alert 的條件。
  4. Affected services 欄位把 service 加到 incident、change；從 graph 看上下游。
  5. 加了 service 不會自動通知或改 priority要通知 owner team 就加 responder；priority 跟 tier 走要寫 automation。
  6. 現行底層是 AssetsSoftware Registry 與 Business Portfolio 兩個 schema；權限看 Assets schema。
本節所有「本段必考」（5 條）
  • Tier＝關鍵程度；references＝依賴。
  • Type 只是標籤。
  • Service 加到 incident 不會自動通知或改 priority。
  • Tier 可當 automation／alert 的條件。
  • 看得到但不能改 → 查 Assets schema 權限。

420.3.3 Products 與 entitlements

品、權、欄Product → entitlement → Entitlement 欄位。
必填即門禁沒權就沒選項。
  1. ProductCustomer 可能有權使用的產品或服務；admin 與 agent 都能新增。
  2. Entitlement某 customer 或 organization 對某 product 的使用權；可附 support level、到期日等 detail。
  3. 啟用Space settings → Features 開 Products and entitlements（考試版）。
  4. 給 organization 建 entitlementOrganization 所有成員都會擁有。
  5. Entitlement 欄位加到 request typeCustomer 只能選自己有權的 product；agent 在 work item 看到 entitlement 細節。
  6. 設成必填＝限制提單沒有 entitlement 的 customer 沒有選項可選，送不出表單。
本節所有「本段必考」（2 條）
  • Entitlement 必填＝限制只有有權的人能提單。
  • Detail fields 要 Jira admin、全站共用、最多 50 個。
420.4・21%

420.4 Customer 端功能

420.4.1 Request types

前台 request type、後台 issue type前台管外觀、後台管流程。
藏＝移出所有 group不是刪除。
限提不限看Restrictions vs issue security。
  1. 一個 request type 只對一個 issue type一個 issue type 可以給很多 request type 用；workflow 與欄位來自 issue type。
  2. Portal groups 決定 portal 怎麼分類一個 request type 可在多個 group；從所有 group 移除＝從 portal 藏起來（搜尋仍找得到）。
  3. Request form vs issue viewRequest form 給 customer 填；issue view 給 agent 看；兩邊欄位分開設定。
  4. Use preset value and hide from portal自動填值並對 customer 隱藏；portal 不支援的欄位（Assignee、Linked issues）只能這樣用。
  5. Status name to show customer替 customer 改 status 的顯示名稱；同名可藏掉 transition。
  6. Restrictions限定哪些 user、group、customer、organization 能提這種單（最多 50 個）；只管「提」，不管「看」。
本節所有「本段必考」（8 條）
  • 一個 request type 只對一個 issue type。
  • 改 work item 的 issue type 就要跟著改 request type。
  • 從所有 portal group 移除＝藏起來（不是刪除）。
  • Create from template 只有 Jira admin。
  • Preset＋hide＝自動填、customer 看不到。
  • Field configuration 必填＝全面；request type 必填＝只有這張表單。
  • 同名 status＝藏 transition。
  • Restrictions 管提單，issue security 管看。

420.4.2 Forms

條件看選項Radio、checkbox、dropdown 才能當條件。
連了才算數Linked Jira field 才能被 JQL、automation、報表用。
鎖＝只剩 admin
  1. 建立Space settings → Request management → Forms：從 200+ 個 template 或 blank 開始；要 Jira admin 或 project admin。
  2. 排版Confluence 風格編輯器：標題、bullets、表格、引用、多欄 layout。
  3. Sections＋條件邏輯依 radio、checkbox、dropdown 的答案顯示或隱藏 section；必填欄位不能放在條件 section。
  4. Linked Jira fieldsForm field 只存在表單裡；連到 Jira field 才能被 JQL、automation、報表使用。
  5. 放在哪Attach to request types、shareable link、加到既有 issue（含 automation 的 Attach forms）。
  6. Preferences保持開放可編輯、每次重送存 PDF、送出後鎖定（只有 admin 能改）、推薦給 agent。
本節所有「本段必考」（6 條）
  • 條件 section 依 radio、checkbox、dropdown。
  • 必填欄位不能放在條件 section。
  • 要給 JQL／automation／報表用 → 連到 Jira field。
  • Forms 不能用在 email、chat、widget、virtual agent。
  • Lock＝送出後只有 admin 能改。
  • 翻譯要開 Available to customers＋portal language support。

420.4.3 Email requests

十個信箱、一信一型最多 10 個 email，每個對一個 request type。
白名單只認 domain、黑名單說了算
  1. 預設 Atlassian email每個 service project 有一個 xxx@公司.atlassian.net；最多連 10 個 email address。
  2. 自訂 emailCreate Atlassian email（新前綴）或 Add external email（Google、Microsoft 用 OAuth；Other 用 IMAP／POP）。
  3. 每個 email 對一個 request typeRequest type 只能 Summary、Description 是必填；多加必填欄位 email 就建不了 request。
  4. Allowlist只填 domain、完全比對；DMARC 啟用時（預設），驗證失敗的信仍會被過濾。
  5. BlocklistDomain 或單一 email address；同時在兩邊時 blocklist 優先。
  6. 關閉Channels & self service → Email → More → Disable all email requests。
本節所有「本段必考」（5 條）
  • 每個 project 最多 10 個 email。
  • Email 的 request type：只有 Summary、Description 能必填。
  • Allowlist 只收 domain；blocklist 收 domain 或 email。
  • 兩邊都有 → blocklist 贏。
  • Email 沒變 request：查 request type 必填欄位、blocklist、customer permissions、logs。

420.4.4 Workflows 與 approvals

核准掛在 status 上Approve、Decline 兩條路。
預設藏起來、自選放出來Preset＋hide vs 放上表單。
  1. 看 request type 用哪個 workflowRequest type → issue type → workflow scheme；Space settings → Workflows 可查看與編輯。
  2. Approval step 掛在 status該 status 至少要有 Approve 與 Decline 兩個 transition；加 approval 要 Jira admin。
  3. Approver 不用授權是 service project 的 customer 就能核准：portal、email、Slack、Teams。
  4. Approver 欄位User picker（multiple users）或 group picker（multiple groups）custom field，加到 request type。
  5. 預設 approver欄位勾 Use preset value and hide from portal，填固定的人或 group（Jira admin）。
  6. 讓 customer 選把 Approvers 欄位放進 request form；customer sharing 要選「space 或 organization 內搜尋」；customer 不能選 group。
本節所有「本段必考」（5 條）
  • Workflow 跟著 issue type，不跟 request type。
  • Approval 要 status 有 Approve 與 Decline 兩個 transition。
  • Exclude approvers 可防止 reporter 自己核准。
  • 預設＝preset＋hide；自己選＝欄位放上表單。
  • Customer 只能選個人 approver。
420.5・12%

420.5 Portal 與通知

420.5.1 Customer portal

名、介、標、公Portal name、introduction、logo、announcement。
顏色找 help center
  1. 品牌Space settings → Channels & self service → Portal：portal 名稱、介紹文字、logo（JPEG／GIF／PNG，建議 50×50）；URL、banner、顏色從 help center 繼承。
  2. 公告Portal 頂端顯示公告；project admin 可勾「Yes, agents can add announcements to this portal」讓 agent 也能發。
  3. Help center 公告Jira admin 發；也可讓 agent 發。
  4. Portal groups把 request type 分組；超過一個 group 才會在 portal 顯示分組（見 420.4.1）。
  5. External resources最多 10 個外部連結，顯示在 portal 的 Related resources。
  6. Language support預設語言＋其他語言；翻譯 portal、request types、customer notifications、email templates、help center。
本節所有「本段必考」（5 條）
  • Portal 的顏色、URL 來自 help center。
  • Agent 發 portal 公告要 project admin 開權限。
  • External resources 最多 10 個。
  • Widget 用 KB → KB 要開放給 Anyone。
  • Customer 看到哪個語言：偏好語言（有翻譯且啟用）→ 否則預設語言。

420.5.2 Virtual agent

招、配、結、閒、升、選Greet、Match、Resolve、Auto-close、Escalate、Offer options。
預設單：不藏、不必填
  1. Intent一個特定問題或請求；有 name、display name、training phrases（官方步驟：輸入三個）與 conversation flow。
  2. AI answers用 generative AI 搜尋連結的知識庫，摘要成回答並附來源文章。
  3. Default request typeVirtual agent 建 work item 時用；不能藏在 portal 外、不能有必填欄位。
  4. Standard flowsGreet、Match intent、Resolve（CSAT）、Auto-close（5 分鐘無動作）、Escalate、Offer options。
  5. Conversations 頁看 Matched／AI answered／Unassisted，Escalated／Resolved／Closed 與 CSAT。
  6. Intent 不支援 emailIntent 在 email 以外的 customer 管道都能用。
本節所有「本段必考」（4 條）
  • 要控制每一句話 → intent；知識庫好就快上線 → AI answers。
  • Default request type：不能隱藏、不能有必填欄位。
  • Display name＝customer 看到的 intent 選項。
  • Unassisted 多＝缺 intent；AI 答了還 escalate＝KB 要更新。

420.5.3 通知與 canned responses

外寄 customer、內走 scheme兩套通知各管各的。
關了還有兩封Resolved、approval required。
共用罐頭靠 admin
  1. Customer notificationsJSM 自己的規則：Space settings → Notifications → Customer notifications；可開關、改主旨與內容、選收件人。
  2. Internal notifications只給 agent 與 admin，依 Jira 的 notification scheme（Jira admin）。
  3. 同時是 agent 與 customerInternal 優先：agent 被指派時改收 internal，取消指派後回到 customer。
  4. Customer 自己關通知仍會收到「request 已解決」與「需要你核准」。
  5. Canned responsesReply to customer／Add internal note → Canned responses；shared（全隊共用）只有 project admin 能建。
  6. Free 方案不能編輯 notification template。
本節所有「本段必考」（6 條）
  • Internal 只給 agent／admin，走 notification scheme。
  • 關了通知仍會收到 resolved 與 approval required。
  • Exclude person who caused the action＝不通知觸發者本人。
  • Reporter 收件人不受 customer 關通知影響。
  • Shared canned response 只有 project admin 能建。
  • Availability 建立後不能改。

420.6 知識庫

420.6.1 知識庫連結與權限

站給選項、專案選、Confluence 守門三層權限。
Anyone 三條件Site 開、Confluence 付費、portal 公開。

  • Unlink 不會刪 Confluence 內容。
  • Anyone＝全網公開、要 site 開＋Confluence 付費＋公開 portal。

  3. 何時出現Customer 在 Summary 欄位打字時。
  4. 限制知識庫連到其他 Confluence site 時，portal 不會顯示 article suggestions。
  5. Agent 也能分享在 issue view 用知識庫面板把文章回覆給 customer。
  6. 看成效KB 報表：文章被看了多少、解決了多少 request（420.7.2）。
本節所有「本段必考」（4 條）
  • Suggestions 逐 request form 開。
  • 用 label 限縮推薦範圍。
  • 跨 site 的 KB 不顯示 suggestions。
  • Label 是連結文章與 request form 的鑰匙。

420.7 報表

420.7.1 JSM 的 JQL

破、曾破、停、跑、完breached、everBreached、paused、running、completed。
ApprovalBy 才是還沒按pendingBy 只看 step 還在等；approver 不管按沒按。
  1. SLAbreached()、everBreached()、completed()、running()、paused()、withinCalendarHours()、elapsed()、remaining()。
  2. Approvalapproved()、pending()、approver(user)、pendingBy(user)、pendingApprovalBy(user)、myPending()、myPendingApproval()。「還沒按」要用 pendingApprovalBy／myPendingApproval。

420.7.2 報表與 dashboards

負、滿、擋、解Workload、Satisfaction、Deflected、Resolved 四張 default。

420.8 Automation

420.8.1 什麼時候用 automation

重複、快違約、更精準、連資產四種該用 automation 的情境。
  1. 重複性工作自動更新欄位、指派、轉 status、寄通知——人每天手動做同一件事，就是 automation 的候選。
  2. SLA 快違約SLA threshold breached trigger：違約前 X 分鐘通知 agent、提高 priority、留言給 customer。
  3. 取代內建通知內建 customer／internal notification 不夠細時，用 automation 寄更貼切的訊息（特定 request type、特定時機、特定收件人）。
  4. 連動 AssetsWork item 到某 status 時，Edit object／Assets 動作把設備的 Status 屬性改成 In repair。
  5. 不是什麼都要 automation一次性的大量修改用 bulk change；每次 transition 必做且要保證一致的用 post function。
  6. Auto-resolve／auto-closeWaiting for customer 超過 N 天沒回 → 自動解決並通知。
本節所有「本段必考」（3 條）
  • 週期性、事件驅動、要判斷條件 → automation。
  • 一次性 → bulk；每次 transition 必做 → post function。
  • 要更「對的人、對的時機、對的內容」→ automation。

420.8.2 設定 automation rule

核、物、時、表Approval、Object、SLA threshold、Form 四種 JSM trigger。
物件看全域、表單看專案Object trigger＝global；form 步驟＝project。
  1. 建立Space settings → Automation → Create rule（自己組，或從 template、或用 AI 描述產生）。
  2. JSM triggersApproval required、Approval completed、Object created／updated／deleted（global）、SLA threshold breached、Form submitted。
  3. JSM conditionsAffected services、Forms attached、AQL。
  4. JSM actionsApprove/decline request、Add service project customer、Create incident、Create work item with a request type、Edit request type、Lookup／Create／Edit object、Attach forms、Copy forms。
  5. Smart values{{issue.summary}}、{{now.plusBusinessDays(3)}}、{{issue.labels.join(", ")}}、{{#=}}…{{/}}、Create variable。
  6. 管理Enable／disable、labels 分類、rule details（owner、actor、scope）。
本節所有「本段必考」（8 條）
  • 一條 rule 只有一個 trigger。
  • Object trigger 只能 global。
  • Form 元件只能 project rule。
  • Edit request type 要同一個 issue type。
  • Auto-close 常用 Scheduled＋JQL。
  • Create variable＋{{變數名}} 重複使用。
  • 數學用 {{#=}}…{{/}}。
  • Labels 只是分類，不影響執行。

420.8.3 排查 automation

範圍、日誌、狀態頁、主人、效能排查五件事。
Owner 收信、actor 動手
  1. Scope單一 project（project admin 可建）vs 多個 project／project type／global（要 Jira admin）；多 project rule 改一次影響全部。
  2. Audit log每次執行的狀態與每一步細節；保留 90 天。
  3. Log action把 smart value 的值寫進 audit log，用來除錯。
  4. Status pageAutomation service status page：確認是不是 Atlassian 服務本身出問題。
  5. Owner錯誤時收 email；人離職或休假要 transfer（Jira admin 用 Transfer user）。
  6. Performance insights執行次數、平均與總時間；Success、No action、Some errors、Loop、Throttled。
本節所有「本段必考」（7 條）
  • 多 project rule 要 Jira admin。
  • Scope 越大，改錯影響越大。
  • No actions performed＝condition 不符，不是錯誤。
  • Log action 是除錯神器。
  • Owner 收錯誤；actor 執行。
  • Transfer user 一次換掉。
  • Throttled＝撞到 service limit。
